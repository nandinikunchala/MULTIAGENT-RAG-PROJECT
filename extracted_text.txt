3.1  RAG in one picture
A plain language model answers from memory and can make things up (‘hallucinate’). RAG ﬁxes
this: you ﬁrst retrieve the most relevant documents, then ask the model to answer only from those.
The answer is grounded and you can show the sources.
PART 3 · AGENTS
3.2  Why three agents instead of one big prompt
You could stuﬀ everything into one prompt. But splitting the work into focused agents — retrieve,
summarize, critique — is more reliable and easier to debug and test. Crucially, the Critic can judge
the Summarizer’s output and demand a better one.
✦ Why LangGraph, not a single LangChain chain (interview gold)
A LangChain chain runs once, top to bottom — it cannot loop back or branch on a later step’s
judgement. Our Critic needs to send weak answers back to the Summarizer. LangGraph gives you two
things a chain can’t: (1) shared state that ﬂows between agents, and (2) conditional routing — the
Critic decides ‘revise’ or ‘ﬁnish’, within a budget that guarantees the loop ends. This is the single most
important design decision in the project; put it in your README.

4.1  Text becomes numbers
An embedding converts text into a vector (a list of numbers) so that similar meanings produce
similar vectors. That’s what lets us ﬁnd ‘the documents most related to this question’. Below, the
local version uses a simple, dependency-free hashing scheme; the production version calls
OpenAI’s embedding model. Both expose the same embed() method.
app/embeddings.py
"""Turns text into a vector so we can measure similarity.
- local: a deterministic hashing bag-of-words embedding (no downloads, no keys)
- production: OpenAI's embedding model (imported lazily)"""
import re, hashlib
import numpy as np
from app.config import MODE
_DIM = 1024
_TOKEN = re.compile(r"[a-z0-9]+")
def _tokens(text: str):
    return _TOKEN.findall(text.lower())
class LocalEmbedder:
    dim = _DIM
    def embed(self, text: str) -> np.ndarray:
        v = np.zeros(_DIM, dtype=np.float32)
        toks = _tokens(text)
        grams = toks + [f"{a}_{b}" for a, b in zip(toks, toks[1:])]  # unigrams + bigrams
        for tok in grams:
            # stable hash so results are reproducible across runs
            idx = int(hashlib.md5(tok.encode()).hexdigest(), 16) % _DIM
            v[idx] += 1.0
        norm = np.linalg.norm(v)
        return v / norm if norm else v
    def embed_batch(self, texts):
        return [self.embed(t) for t in texts]
class OpenAIEmbedder:
    dim = 1536
    def __init__(self):
        from langchain_openai import OpenAIEmbeddings          # lazy import
        self._model = OpenAIEmbeddings(model="text-embedding-3-small")
    def embed(self, text: str):
        return np.array(self._model.embed_query(text), dtype=np.float32)
    def embed_batch(self, texts):
        return [np.array(v, dtype=np.float32) for v in self._model.embed_documents(texts)]
def get_embedder():
    return OpenAIEmbedder() if MODE == "production" else LocalEmbedder()

5.1  Finding the nearest vectors
The store keeps every document’s vector and, given a query vector, returns the most similar ones
by cosine similarity (a score from −1 to 1; higher = more related). The in-memory version is a
few lines of NumPy; the production version is Pinecone. Same interface.
app/vectorstore.py
"""Stores document vectors and finds the most similar ones to a query.
- local: an in-memory cosine-similarity store (no external DB)
- production: Pinecone (imported lazily)"""
import numpy as np
from app.config import MODE, PINECONE_API_KEY, PINECONE_INDEX
class InMemoryStore:
    def __init__(self, embedder):
        self.embedder = embedder
        self._ids, self._texts, self._vecs = [], [], []
    def upsert(self, doc_id: str, text: str):
        self._ids.append(doc_id)
        self._texts.append(text)
        self._vecs.append(self.embedder.embed(text))
    def search(self, query: str, k: int = 3):
        if not self._vecs:
            return []
        q = self.embedder.embed(query)
        mat = np.vstack(self._vecs)
        scores = mat @ q                      # cosine sim (vectors are normalised)
        order = np.argsort(scores)[::-1][:k]
        return [{"id": self._ids[i], "text": self._texts[i], "score": float(scores[i])}
                for i in order]
class PineconeStore:
    def __init__(self, embedder):
        from pinecone import Pinecone         # lazy import
        self.embedder = embedder
        pc = Pinecone(api_key=PINECONE_API_KEY)
        self.index = pc.Index(PINECONE_INDEX)
    def upsert(self, doc_id: str, text: str):
        vec = self.embedder.embed(text).tolist()
        self.index.upsert([(doc_id, vec, {"text": text})])
    def search(self, query: str, k: int = 3):
        q = self.embedder.embed(query).tolist()
        res = self.index.query(vector=q, top_k=k, include_metadata=True)
        return [{"id": m["id"], "text": m["metadata"]["text"], "score": m["score"]}
                for m in res["matches"]]
def get_store(embedder):
    return PineconeStore(embedder) if MODE == "production" else InMemoryStore(embedder)

6.1  Chunk, embed, upsert
Long documents are split into overlapping chunks so retrieval is precise (you fetch the relevant
paragraph, not a whole book). Each chunk is embedded and stored.
app/ingest.py
"""Load the knowledge base from data/docs, chunk it, and upsert into the store."""
import os, glob
from app.embeddings import get_embedder
from app.vectorstore import get_store
DOCS_DIR = os.path.join(os.path.dirname(__file__), "..", "data", "docs")
def _chunk(text, size=500, overlap=80):
    """Split long text into overlapping chunks so retrieval is granular."""
    words = text.split()
    chunks, i = [], 0
    while i < len(words):
        chunks.append(" ".join(words[i:i + size]))
        i += size - overlap
    return chunks or [text]
def build_store():
    embedder = get_embedder()
    store = get_store(embedder)
    for path in sorted(glob.glob(os.path.join(DOCS_DIR, "*.md"))):
        name = os.path.splitext(os.path.basename(path))[0]
        text = open(path, encoding="utf-8").read()
        for j, chunk in enumerate(_chunk(text)):
            store.upsert(f"{name}#{j}", chunk)
    return store

7.1  Two brains, one interface
Both the summarizer and critic need ‘thinking’. We expose two task methods — summarize() and
critique() — so the agents don’t care which backend runs. The local brain is deterministic
(extractive summary + a grounding check); the OpenAI brain uses carefully written prompts.
app/llm.py
"""The 'brains' behind the summarizer and critic agents.
Both implementations expose the SAME two task methods, so the agents don't
care which one they're using:
- LocalLLM: deterministic, offline (extractive summary + grounding-based critique)
- OpenAILLM: real LLM calls with carefully engineered prompts (production)"""
import re
from app.config import MODE
_SENT = re.compile(r"(?<=[.!?])\s+")
_WORD = re.compile(r"[a-z0-9]+")
_STOP = {"the", "a", "an", "of", "to", "in", "and", "or", "is", "are", "was",
         "were", "for", "on", "with", "as", "by", "that", "this", "it", "how",
         "what", "why", "does", "do", "which", "who", "when"}
def _content_words(text):
    return {w for w in _WORD.findall(text.lower()) if w not in _STOP and len(w) > 2}
class LocalLLM:
    """No API calls. Good enough to exercise the full agent pipeline in tests."""
    def summarize(self, query, docs, revisions=0):
        # Rank every sentence in the retrieved docs by overlap with the query,
        # then keep the top (2 + revisions) - more passes -> a fuller answer.
        q_words = _content_words(query)
        sentences = []
        for d in docs:
            for s in _SENT.split(d["text"]):
                s = s.strip()
                if s:
                    overlap = len(q_words & _content_words(s))
                    sentences.append((overlap, s))
        sentences.sort(key=lambda t: t[0], reverse=True)
        top = [s for score, s in sentences[: 2 + revisions] if score > 0] \
            or [s for _, s in sentences[:1]]
        return " ".join(top)
    def critique(self, query, summary):
        # Grounding check: does the summary actually cover the query's key terms?
        need = _content_words(query)
        have = _content_words(summary)
        missing = sorted(need - have)
        covered = 1.0 if not need else (len(need & have) / len(need))
        verdict = "pass" if covered >= 0.6 else "revise"
        issues = [] if verdict == "pass" else [f"missing coverage of: {', '.join(missing)}"]
        return verdict, issues
class OpenAILLM:
    def __init__(self):

        from langchain_openai import ChatOpenAI              # lazy import

                                   HumanMessage(content=user)])

        context = "\n\n".join(f"[{d['id']}] {d['text']}" for d in docs)
        system = ("You are a precise research summarizer. Answer ONLY from the "
                  "provided sources. Cite source ids like [id]. If the sources do "
                  "not answer the question, say so.")
        user = f"Question: {query}\n\nSources:\n{context}\n\nWrite a concise, cited answer."
        return self._chat(system, user)
    def critique(self, query, summary):
        system = ("You are a fact-checking critic. Decide if the summary is fully "
                  "supported and answers the question. Reply 'PASS' or 'REVISE: "
                  "<reason>'.")
        user = f"Question: {query}\n\nSummary:\n{summary}"
        out = self._chat(system, user)
        if out.upper().startswith("PASS"):
            return "pass", []
        return "revise", [out]
def get_llm():
    return OpenAILLM() if MODE == "production" else LocalLLM()

8.1  Single-responsibility agents
Each agent owns exactly one step. Keeping them thin makes the system easy to reason about, test,
and extend (you could add a ‘translator’ agent without touching the others).
app/agents.py
"""Three single-responsibility agents. Each owns one step of the pipeline."""
class RetrieverAgent:
    """Finds the most relevant documents for a query (RAG retrieval step)."""
    def __init__(self, store, top_k=3):
        self.store, self.top_k = store, top_k
    def run(self, query):
        return self.store.search(query, k=self.top_k)
class SummarizerAgent:
    """Turns retrieved documents into a grounded answer."""
    def __init__(self, llm):
        self.llm = llm
    def run(self, query, docs, revisions=0):
        return self.llm.summarize(query, docs, revisions)
class CriticAgent:
    """Fact-checks the summary against the question; may request a revision."""
    def __init__(self, llm):
        self.llm = llm
    def run(self, query, summary):
        verdict, issues = self.llm.critique(query, summary)
        return {"verdict": verdict, "issues": issues}

9.1  Wiring agents into a graph
This is the heart of the project. A StateGraph deﬁnes the shared state and the nodes; edges
deﬁne the ﬂow. The special part is add_conditional_edges: after the critic runs, a route function
decides whether to loop back to the summarizer or ﬁnish.
app/graph.py
"""The LangGraph orchestration: retrieve -> summarize -> critique, with a
conditional loop back to summarize when the critic asks for a revision.
THIS is why LangGraph beats a single LangChain chain:
- shared STATE flows between agents (docs, summary, critique, revision count)
- CONDITIONAL ROUTING lets the critic send work back for another pass
A linear chain cannot loop or branch on a downstream agent's judgement."""
from typing import TypedDict, List, Dict
from langgraph.graph import StateGraph, END
from app.config import MAX_REVISIONS
class ResearchState(TypedDict):
    query: str
    docs: List[Dict]
    summary: str
    verdict: str
    issues: List[str]
    revisions: int
def build_graph(retriever, summarizer, critic, max_revisions: int = MAX_REVISIONS):
    def retrieve_node(state):
        return {"docs": retriever.run(state["query"])}
    def summarize_node(state):
        summary = summarizer.run(state["query"], state["docs"], state.get("revisions", 0))
        return {"summary": summary}
    def critique_node(state):
        result = critic.run(state["query"], state["summary"])
        return {"verdict": result["verdict"],
                "issues": result["issues"],
                "revisions": state.get("revisions", 0) + 1}
    def route(state):
        # branch on the critic's judgement + a revision budget
        if state["verdict"] == "revise" and state["revisions"] <= max_revisions:
            return "summarize"      # hand back for another attempt
        return "end"
    g = StateGraph(ResearchState)
    g.add_node("retrieve", retrieve_node)
    g.add_node("summarize", summarize_node)
    g.add_node("critique", critique_node)
    g.set_entry_point("retrieve")
    g.add_edge("retrieve", "summarize")
    g.add_edge("summarize", "critique")
    g.add_conditional_edges("critique", route, {"summarize": "summarize", "end": END})
    return g.compile()

route() is the entire argument for using LangGraph. It inspects the critic’s verdict and the revisions

guarantees the loop always terminates — there’s a test proving it (Part 13).

"""Compute retrieval precision@k and recall@k over the test set.
Run with:  python -m eval.run_eval"""
from app.ingest import build_store
from app.config import TOP_K
from eval.testset import TEST_QUERIES
def _base(doc_id):            # 'photosynthesis#0' -> 'photosynthesis'
    return doc_id.split("#")[0]
def evaluate(k=TOP_K):
    store = build_store()
    hits, top1_hits, precisions = 0, 0, []
    print(f"\nRetrieval evaluation (top_k={k}) over {len(TEST_QUERIES)} queries\n" + "-" * 60)
    for query, expected in TEST_QUERIES:
        results = store.search(query, k=k)
        retrieved = [_base(r["id"]) for r in results]
        relevant = sum(1 for r in retrieved if r == expected)
        precision = relevant / k
        precisions.append(precision)
        top1 = retrieved[0] if retrieved else "-"
        ok = "OK " if expected in retrieved else "MISS"

        hits += expected in retrieved

    print(f"Top-1 accuracy:            {top1_hits}/{len(TEST_QUERIES)} =

15.1  Put your reasoning in the README
This is the diﬀerence between ‘a student wired some libraries together’ and ‘an engineer made

README.md
# Multi-Agent RAG Research Assistant
Three cooperating agents answer a question from a document knowledge base:
a **Retriever** (RAG), a **Summarizer**, and a **Critic** that fact-checks the
answer and can send it back for revision - orchestrated with **LangGraph**.
Runs fully offline in `MODE=local`; uses **OpenAI + Pinecone** in `MODE=production`.
## Architecture
retrieve --> summarize --> critique --> (revise? loop back : finish)
## Design Decisions
**Why LangGraph over a single LangChain chain** - the critic must be able to
send work *back* to the summarizer for another pass. A linear chain runs once,
top to bottom, and cannot loop or branch on a later agent's judgement.
LangGraph gives us (1) shared **state** that flows between agents and (2)
**conditional routing** (`add_conditional_edges`) so the critic decides whether
to finish or revise, within a revision budget that guarantees termination.
**Agent handoff logic** - state carries `query -> docs -> summary -> verdict`.
Retriever writes `docs`; summarizer reads `docs` + `revisions` and writes
`summary`; critic reads `summary` and writes `verdict`/`issues` and increments
`revisions`. The router reads `verdict` + `revisions` to route back or end.
**RAG design** - documents are chunked with overlap, embedded, and stored in a
vector index; retrieval uses cosine similarity. Swapping local <-> Pinecone is a
one-line change because the store is behind a small interface.
**Testability** - LLM, embeddings, and vector store each have a local
implementation, so the full pipeline is unit-tested offline with no API keys.
## Retrieval evaluation
`python -m eval.run_eval` scores 15 queries -> Recall@3 = 100%, top-1 = 80%
on the local embedder (production embeddings score higher).
